## Plan (lead, 2026-11-09, revised the same night)
- **Why it shows at once, from the code:** `setup.init` (`runner/setup.py`) ends with `register`, which writes the project's row "setting up" before `os.execvp` hands the terminal to Claude (`_machine_command`, `runner/cli.py`). The Projects page lists that row from then on. `softfield doctor`, run by Claude as the setup's last step, only lifts the pause.
- **A trap in the way:** `softfield accept 0` (`owner.decide_adr` → `owner._write`) calls `upsert_project`, which *creates* a missing row with no pause. With `init` no longer registering, accepting ADR 00 would put a half-set-up project on the runner's line. f236-01 closes it.
- **Revised on the owner's comment** (2026-11-09: "doctor doesn't sound like it will finish the init step … maybe a softfield create after init which will run doctor before the final creation. Claude could suggest or run it for me"): an explicit `softfield create` replaces "doctor registers" and "registered on exit". `doctor` goes back to only checking.
- **Found on the same thread (coaster-ranker, 2026-11-09):** `doctor` passed and handed coaster-ranker over at 21:34, but the runner has never opened a session for it (no row in `runs`), so its "Plan this card." job (work_queue 662) has waited since 22:38 while later softfield jobs ran. `run_projects` (`runner/loop.py`) skips a project whose `open_session` refuses (not on main, or uncommitted changes) and says so once, in its console only; the Projects page says "nothing for you". f236-03 puts it on the desk.
- **It waits for F136, softfield init asks what to do with a forgotten project of the same name:** f136-02 and f136-03 rewrite `init` and `register` too; building on them avoids two lead tickets clashing in the same functions. f236-03 waits for nothing.
- Tickets, all lead (`runner/**` is protected): `f236-01-doctor-registers-the-project` (it builds `softfield create`: the id predates the revision), then `f236-02-setup-ends-at-the-session-exit`; `f236-03-a-project-that-cant-start-says-why` on its own.
- No mock-up: f236-01 and 02 are in the terminal. f236-03 adds an item to the existing Planning desk with the desk's own look and makes the Projects page's existing "N for you" count it; nothing new is drawn.

## Decisions
- **D1: `softfield create` adds the project, and only it.** `init` writes, commits and asks F136's question, but writes no row. `softfield create`, in the project's folder, runs everything `doctor` checks (check-all included) and prints them; when every needed one passes it registers the project under `.softfield/project.toml`'s `name`, last in the owner's order and not paused, publishes its cards, asks the lead to plan the first one, and prints the hand-over lines (`hand_over`), as `doctor` does today. When one fails it prints what's left and "Nothing was added to the factory." A name a live project in another folder holds is refused with a message (F136 D2). F136's "continue" un-forgets its row only here, and "keep" renames the old row at `init` but registers the new one only here. `softfield create` on a registered project says so and does nothing.
- **D2: `doctor` only checks, everywhere.** Its "registered as …" finding goes, so does the `ready` hand-over in its branch; when everything passes on a project not yet registered its last line is "Ready: `softfield create` adds {name} to the factory." On a registered project it is a health check, as `doctor` reads.
- **D3: nothing else creates a row.** `owner._write` (`softfield accept`, `reject`…) writes only to a project that is registered, and skips silently otherwise: there is nothing on the desk to resolve yet.
- **D4: Claude asks, then runs it.** bootstrap.md's last step: after `softfield accept 0`, Claude runs `softfield doctor` and fixes what it says; when it passes, Claude asks "Ready to add {name} to the factory?" and on the owner's yes runs `softfield create` itself, then ends with its hand-over lines and "You can leave this session now (/exit)." Claude never runs `create` without that yes.
- **D5: leaving early is safe.** `init` runs Claude as a child process (not `execvp`). When Claude exits and the project isn't registered, `init` prints "{name} isn't in the factory yet." and "To finish: `softfield init` here again carries on with Claude, or `softfield create` adds it if it's ready." It doesn't create on its own.
- **D6: `init` again carries on.** In a folder whose `.softfield/project.toml` exists but whose project no live row holds, `init` writes nothing and opens the setup session again with "Carry on the setup of {name}: run `softfield doctor` first and pick up from what it says." A registered project is refused as today.
- **D7: a project the runner can't open is on the desk.** When `open_session` refuses a registered, unpaused project, `run_projects` records an owner item on that project (kind `cant_start`, subject the project's name) whose text says why in plain words and, for uncommitted changes, lists up to ten of the paths git reports. It is resolved the round a session opens. Opening is retried every round as today, so the item clears by itself once the folder is fixed.
- **D8: ADR 30's record.** Item 7 ("the project registered in the DB"), item 8 (`doctor`) and the "A project is paused while it is set up" note get a dated line: changed by F236, `softfield create` registers the project once `doctor`'s checks pass, on the owner's yes. The owner's approval of this plan is the decision.
