# Notes for developers on Softfield

Short on purpose: at most 15 notes (ADR 07). The lead keeps them current. The ones that hold in any project are the package's (`runner/instructions/developer.md`).

## Worked examples: copy their shape
- Dashboard page: `factory_dashboard/overview.py` (an `APIRouter` with its own SQL, included in `app.py`'s `create_app`) + `factory_dashboard/templates/overview.html` (extends `base.html`; a chart is a `data-chart` div, its JSON and a function in `static/charts.js`) → `tests/factory_dashboard/test_overview.py` (checks the rendered text and each chart's JSON)
- Factory line: the data and every rule in Python, `factory_dashboard/line.py` (`live_line`, a JSON block in the page; `line.py` imports from `overview.py`, so `overview.py` imports `live_line` inside `_live_context`, never at the top); the drawing only in `factory_dashboard/static/factory.js` (hand-written SVG) → `tests/factory_dashboard/test_line.py` (tests on the JSON, plus one browser test: the page from `TestClient`, `/static/` from disk with `page.route`)
- A station on the floor that opens the card: `showSeeds` in `factory_dashboard/static/factory.js` (a `data-` attribute on the station, found by the two listeners at the end of the file; the card is filled with `el` and `fillCard`, its list from the drawn document, here `field.later` from `_field` in `line.py`) → `set_aside` and the three tests after it in `tests/factory_dashboard/test_line.py` (redraw the floor with a list you choose, then assert every link's `href` and text)
- Dashboard script with behaviour: `factory_dashboard/static/notify.js` (reads `data-` attributes a partial renders, acts after `htmx:afterSwap`; the facts are computed in Python) → `tests/factory_dashboard/test_app.py` (the attributes asserted from the HTML; one browser test replaces the browser API with a recording stand-in, `page.add_init_script`, and asserts what was called)
- A live part's 5 s refresh in a browser: `open_overview` and the two tests after it in `tests/factory_dashboard/test_overview.py` (`/` and `/live` rendered on every request, the database changed between polls, waits longer than 5 s)
- A panel drawn from the line document, with numbers you choose: `with_clog` and the four tests after it in `tests/factory_dashboard/test_overview.py` (monkeypatch `factory_dashboard.line.live_line` to call the real one and then set one key; the rule lives in a small function in `overview.py`, not in `line.py`)
- Dashboard colours and fonts: new UI uses the tokens, never raw colours. Pick from the `:root` block at the top of `factory_dashboard/static/dashboard.css` (`--floor`, `--bay`, `--plate`, `--rule`, `--hazard`, `--fail`, the agents' `--opus`, `--qwen`…, `--display`, `--body`, `--mono`); the light theme only redefines them, so a raw `#hex` stays dark in light mode. A mock-up's markup is a picture, not code to paste: map each of its `#hex` colours to the nearest token (f6-06 pasted them), and leave out its notes to the owner (`class="note"`, "▲ new bay": f80-01 put one on the page). E.g. the allowance meters: `.meter > .past-mark { background: var(--hazard); }` → `test_an_allowance_meter_says_how_close_it_is` in `tests/factory_dashboard/test_app.py` (`test_templates_use_the_tokens_never_raw_colours` fails a raw colour in a template)
- A button that asks the runner: `POST /requests` in `factory_dashboard/requests.py`, the dashboard's only write (one `owner_requests` row; never write anywhere else, and never through `Db`, which is read-only). The button is `hx-post="/requests"` with `hx-vals` for `kind`, `subject` or `value` and `project`; it swaps in `_partials/request.html`, which polls the request until the runner finishes it → `tests/factory_dashboard/test_requests.py` (send the `HX-Request` header and the client's own `Origin`; without them the route answers 403). Assert what a button posts, not that it exists: `_posts` in `tests/factory_dashboard/test_planning.py` parses its `hx-vals` as JSON, so a broken one fails (f6-08's had no closing brace and its tests checked only the button's id); a git checkout for the project is the `checkout` fixture in `tests/factory_dashboard/conftest.py`
- Asserting a page's text: Jinja escapes it (`'` becomes `&#39;`, so "the lead's" never matches the raw string), so strip the tags and `unescape` first, and assert within the item, not the whole page: `_text` and `_points` in `tests/factory_dashboard/test_planning.py` (f6-07 spent an attempt on an answer "missing" from the HTML)
- Showing part of a page on a phone: `factory_dashboard/static/deck.js` (toggles a class; the rule lives in `dashboard.css` under a media query, with `!important` because the points carry an inline `display`, which beats any stylesheet rule and the `hidden` attribute) → `test_on_a_phone_one_point_shows_at_a_time` in `tests/factory_dashboard/test_thread.py` (asserts what the browser draws with `is_visible()` and `bounding_box()`, never the `hidden` property or a selector like `[hidden=false]`: f6-10's test passed while all seven points stayed on screen). A phone row out of a desktop column: the f42 block at the end of that media query (sets `flex-direction`, since `display: flex` alone keeps the desktop rule's `column`; `min-width: 0` lets the count wrap) → `test_the_dock_is_compact_on_a_phone` (reads each control's `bounding_box()` inside the dock's; a control the page starts `hidden`, like `#send-back`, is never asserted visible)
- Counting what happened in a span of time: `queries.away` → `write_away` and the test after it in `tests/factory_dashboard/test_overview.py` (times are parsed with `_time` and compared as moments, never as ISO strings in SQL: the runner writes its own offset; the fixture is its own database in `tmp_path`, and each job has its own attempt)
- Numbers for a week by local Monday: `factory_dashboard/reports.py` (`week`, `weeks`; local midnight with that date's own offset, `datetime(y, m, d).astimezone()`) → `tests/factory_dashboard/test_reports.py` (a small fixture of its own whose docstring lists every job, times built with `_at`, each assertion a whole dict or an exact number: never `>=`, or `"f1-01" not in str(found)`, which can't fail; when a number surprises you, run the test and read what it got, don't reason about it: f59-01 spent an attempt that way)
- A count that must equal another module's: `live_line`'s five field counts from `board` (`factory_dashboard/line.py`, the import inside the function) → `board_counts` and `test_the_field_stations_count_the_board_s_cards` in `tests/factory_dashboard/test_line.py` (the test calls the other module on the same database and compares; never work a fixture's numbers out by hand first: f3-08 read for three attempts doing that and made no edit)
- A part of a page drawn again after a post: the `htmx:afterRequest` listener in `factory_dashboard/templates/planning.html` (`htmx.ajax` with `target` and `select`, never `fetch` + `replaceChild`: htmx must bind the new markup, or the new form's next send leaves as a plain GET; listeners go on the document, since the element they'd sit on is replaced) → `test_a_second_plant_adds_a_second_row` in `tests/factory_dashboard/test_coming.py` (send twice from the same page, and wait for something only the second re-fetch brings; "shows at once" is asserted on the page as it stands, never after `page.reload()`, which passes with no listener at all: `test_edit_then_save_posts_a_change_and_the_message_shows_it_at_once` in `tests/factory_dashboard/test_thread.py`)
- A card that says more in one view of a page: `dev_tag` and `card_link` in `factory_dashboard/templates/board.html` (the data is `None` outside the view, so the macro tests it and keeps its one argument; never pass a new argument to a macro before its `{% macro %}` line takes it: f146-02 did, and every board page failed) → `test_each_planted_card_says_what_it_holds_for_developers` in `tests/factory_dashboard/test_board.py`
- A page's inline styles moved into the stylesheet: the f81-05 block for `thread.html` and `proposal.html` in `factory_dashboard/static/dashboard.css` (every rule under the page's root class, `.thread-page …`; a colour set per item stays in the template as `style="--c: var(…)"`, since the CSS holds no `{{ }}`; a state is an attribute, `.message[data-waiting]`; an element that already has a class gets no second one, because tests match `class="message"` exactly) → `test_send_with_comments_posts_one_request` in `tests/factory_dashboard/test_thread.py` (reads the drawn border with `getComputedStyle`, not the markup)
