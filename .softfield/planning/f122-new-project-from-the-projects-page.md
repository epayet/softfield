>
> 1. **Does the original seed still make sense?**: Mostly, yes. Three parts still hold: the page sends a request, the runner does what `init` does, and the setup happens on the Planning desk. Four things have changed since 14 October. (1) F236, softfield init adds the project only when its setup ends and doctor passes, made `softfield create` the step that adds a project, and only on your yes. On the web, that yes is your Approve on ADR 00. (2) ADR 46 brought Docker stacks, so the stack can go into the setup itself. (3) The folder comes from a setting instead of a fixed `~/projects`. (4) The setup is one round instead of a chat (point 3). The seed's three open questions are answered in points 4 and 7.
>    Action: The card doc now has a Plan, Decisions D1 to D6, Tickets and a Later list. Your notes are unchanged.
> 2. **Does it have to wait for the runner? Yes, and that's fine**: Making the folder could happen at once if the dashboard did it itself, the way Run and Stop do Docker. I recommend against it, for two reasons. First, it would give the dashboard write access to your home folder, which is a much bigger exception to ADR 18 than Docker's four fixed commands. Second, it saves nothing in the end, because the Claude part has to wait for the runner anyway. So the page sends a `new_project` request and the runner makes the folder at its next pick. That step needs no Claude: `init`, your idea saved word for word in `seed.md`, and the M1 card. Your words are on disk before any job runs. The plate shows up the moment you press Start, with the dashed orange 'on its way' edge.
>    Action: Tickets f122-01 and f122-02; ADR 48 items 1 and 4.
> 3. **How interactive can it be? One round, on purpose**: Every reply on a thread is a job that waits for the Claude lane. This month, 36 of 107 planner jobs started within 5 minutes of your message, 18 within 30 minutes, 15 within 2 hours, and 38 waited more than 2 hours (pauses, the reserve, nights). Asking one question at a time, as the terminal does, would take days. So the form asks up front what the terminal asks one by one: the idea, a name, what to build it with (optional), and whether it's a browser app. The lead then does everything in one go, says what it decided and why, and replies on M1's thread with ADR 00 to approve. It asks only what it truly can't decide. You can still write back on the thread, and each message queues another setup round. For a long live talk, `softfield init` in a terminal stays.
>    Action: ADR 48 item 5; f122-02 adds a 'From the Projects page' section to bootstrap.md.
> 4. **Where the folder goes: a line in factory.toml, no new command**: Use `[projects] root` in `~/.config/softfield/factory.toml`. Without it, the default is the folder all your live projects already share, and for you that is already `~/projects/epayet` (coucou, softfield, travel-companion and coaster-ranker all live there). So you have nothing to set. I'd push back on a `softfield config` command: it's a command for one key, and the file is already edited by hand for `[notify]`. The form shows the full path the project will go to before you press Start. A name that's already taken gets `-2` instead of being refused (your 'never refuse my words' rule). A forgotten project with the same name gets F136's 'keep'.
>    Action: f122-01 (D1).
> 5. **Docker from day one: in the setup, not in M1's tickets**: I agree with the goal, and I'd go one step earlier than you suggested. When you tick 'It's an app I open in a browser' (ticked by default), the setup follows run-stack.md: `compose.yaml`, a free port in the 8100–8199 range, `[run]`, and a skeleton that serves one page. Run then shows on the plate the moment the project joins, before any ticket has run. Putting it in M1's tickets would leave a stretch with no Run button, and planting it later would cost a whole card. The catch: no job may run Docker (ADR 46 item 7), so the stack is first tested when you press Run. If it crashes, the existing 'Plant a card to fix it' button covers it. The terminal setup gets the same step.
>    Action: f122-02 (D5); ADR 48 item 7.
> 6. **Mock-ups get reviewed on M1's thread, as for any card**: Agreed: setup stays minimal and draws no product mock-ups. The setup conversation happens on M1's thread. Once your Approve adds the project, the lead is asked right away to plan M1 on that same thread, mock-ups included (F72). That gives you one thread from the idea to the first plan, and no separate setup card to archive afterwards.
>    Action: f122-03 (D4).
> 7. **The seed's other two questions: ADR 00 from the web, and trust**: ADR 00 from the web: the planning room already has an Approve for `adr` proposals (`_accept_adr`, runner/requests.py). It commits 'ADR 0 accepted by the owner', which is exactly what doctor checks for. So the setup only has to propose ADR 00 that way. Trust: this isn't a problem. Headless jobs already run with `--permission-mode dontAsk` and an allow-list in any folder (runner/claude.py), as they do today in coaster-ranker.
>    Action: Nothing new beyond f122-02 and 03.
> 8. **Approve on ADR 00 also adds the project to the factory**: Approving ADR 00 counts as your yes, the same yes F236 asks for in the terminal ('Ready to add it?'). The runner then runs `create`'s checks, including check-all. If they pass, the project goes to the runner and M1 is planned. If they fail, the lead is sent back with what failed, at most twice; after that, the desk says where the setup stopped. That saves you a second button.
>    Action: f122-03; ADR 48 item 6.
> 9. **Deviation: a web project shows before ADR 00 is accepted**: F236's D1 says only `create` adds a project. F236's rule still holds in the terminal. The runner gives a project that is being set up only setup jobs.

> 13. **Should a new app start by itself when it joins?**: My recommendation is no. You press Run when you want it, and an app that starts itself uses memory beside the local model. The other choices: (a) it starts once when the project joins, so a crash shows at once; (b) it starts once, then stops after a successful start, to prove the stack works.
