## Outcome

- Every run writes its facts to one metrics database as they happen: runs, tickets and the queue, every job with its tokens, time, gates and outcome, findings, limit pauses and what needs the owner. M1–M4 are backfilled from what's left of their logs.
- `uv run runner dashboard` serves a local site at `127.0.0.1`: Overview (with **Needs you** and what's running now, live), Milestones, Tickets, Jobs, Runs, Timeline, Agents, Bench and a project page. Every item has its own URL.
- `uv run runner report <key>` writes a milestone review's numbers from the same queries, savings from delegating included (in dollars).
- "Junior" is now "developer". Tickets carry `difficulty:`. Agents and roles are declared in `workflow/runner.toml`, behind one job spec with an adapter per harness (Claude, OpenCode, Copilot). Developers have ratings, a router picks who does a ticket, Copilot can shadow checkpoints, and `runner bench` replays a ticket for any agent.
- A closing factory review (f1-32) looks at the whole flow with the evidence the database now holds.

  - One page module per URL group, one test file per page module; the layout gate, `check-all`'s `TEST_DIRS` and the hatch packages learn `tests/factory_dashboard` ↔ `factory_dashboard` (f1-05).
  - `factory_dashboard` imports nothing from `coucou/` and never writes the database. `runner report` imports `factory_dashboard.queries`; `tests/runner/test_report.py` pins its numbers.
- **D2 Database:**
  - Path: `[metrics] db` in `workflow/runner.toml`, default `~/.local/share/software-factory/factory-metrics.sqlite`, WAL mode. Tests always use a temporary path.
  - Times are ISO-8601 text with an offset. JSON columns hold lists or objects.
  - Tables and the columns other tickets rely on (f1-01 may add more):
    - `projects`: `name` (the repo folder name), `repo`, `description`
    - `milestones`: `project_id`, `key` (`m4`, `f1`), `title`, `status`, `started`, `ended`, `verdict`, `review_rounds`, `review_score`, `owner_score`, `outcome`, `done_when`, `signoff` (JSON: `changed`, `how_to_test`, `what_next`, `later`, `lessons`)
    - `runs`: `project_id`, `run_dir` (`20260930-152311`), `command`, `started`, `ended`, `heartbeat`, `verdict`
    - `tickets`: `project_id`, `milestone_id`, `ticket` (the id, `m4-06-me-wiring`), `title` (the goal), `body`, `kind` (`lead` / `developer`), `depends_on`, `files` (JSON), `state` (`ready`, `running`, `done`, `escalated`, `blocked`), `difficulty`, `difficulty_corrected`, `merged_by`, `commit`, `lines_changed`
    - `jobs`: `run_id`, `ticket_id` (null for milestone-wide jobs), `milestone_id`, `role`, `agent`, `attempt`, `started`, `ended`, `outcome` (`running`, `passed`, `failed`, `timeout`, `refused`), `tokens_in`, `tokens_cached`, `tokens_out`, `requests`, `cost_usd`, `steps`, `peak_context`, `context_limit`, `edit_streak`, `refused_commands`, `routing_reason`, `gates` (JSON `[{name, ok, seconds, log}]`), `note`, `session_id`, `log_path`
    - `findings`: `job_id`, `milestone_id`, `ticket_id`, `key` (`m4-F1`), `severity`, `route`, `file`, `line`, `summary`, `detail`, `agent`, `verdict`, `resolved`
    - `rating_changes`: `agent`, `skill` (`coding` / `reviewing`: what moved the agent's one rating, ADR 15 item 9), `before`, `after`, `ticket_id`, `result`, `at`
    - `usage_events`: `agent`, `at`, `kind` (`refusal`, `reset`, `reading`), `value` (a reading is the fraction of the window used, 0–1), `resets_at`; f1-44 adds `window` (`five_hour`, `seven_day`, `month`)
    - `owner_items`: `project_id`, `kind`, `subject`, `text`, `command`, `created`, `resolved`
  - Natural keys make every write idempotent: (project, run_dir), (project, ticket), (run, ticket, role, attempt), (milestone, finding key).
- **D3 Live:**
  - A job row is written at its start (`outcome = running`) and finished at its end.
  - OpenCode's stream is read line by line into its log; every 30 s the runner updates the running job's tokens and steps, and its run's `heartbeat`.
  - Claude jobs show elapsed time only, until they finish.
  - The dashboard never parses harness logs (ADR 13: only adapters know harnesses).
  - **No extra process:** the dashboard is a plain server the owner starts when wanted; its pages poll (htmx, every 5 s) only while open. "Running now" = jobs still `running` whose run's heartbeat is under 2 min old. A stale one shows as a Needs-you item, computed by the dashboard (a dead runner can't write it).
  - **Amended 2026-10-02 (the owner watching f1, f1-51):**
    - Claude jobs report tokens and steps live too, read from their stream-json as it arrives, like OpenCode's.
    - `runs` gains `activity` (a short text: "gates · f1-21", "check-all on main", "warm-up", "waiting for Claude"), `waiting_until` (when a pause for a limit ends) and `reserve` (1 once the owner said yes to the reserve for this command). Running now shows the activity when no job runs, "waiting for Claude until HH:MM" instead of a running job, and an "on the reserve" badge.
- **D4 Queue:** the runner upserts every ticket's folder state at session start and on each move. The Overview reads the queue from the database, not from `tasks/`, and gives the command that drains it (`uv run runner milestone <key>`).
- **D5 Charts:** a `<div data-chart="<kind>">` followed by a `<script type="application/json">` data block; `factory_dashboard/static/charts.js` has one function per kind, drawing with ECharts. Tests check the JSON a route renders, not the drawing; the review takes screenshots.
- **D6 Ids and agents:**
  - Agent ids are `<harness>-<model>` (ADR 14 item 2). Backfilled and current jobs: `local-qwen3.6-35b-a3b`, `claude-opus`, and `claude-sonnet` for checkpoints.
  - **From f1-18's probes:** Ollama agents are `ollama-<tag>` without its `-cloud` or `:cloud`, with `:` as `-`, with model `ollama/<tag>` (`ollama-gpt-oss-120b` → `ollama/gpt-oss:120b-cloud`; `ollama-nemotron-3-super` → `ollama/nemotron-3-super:cloud`). Copilot is `copilot-auto` with model `auto`: Free's models are unknown, and named ones failed.
  - Roles are ADR 14's `[roles]` names (`developer`, `last-attempt`, `direction`, `checkpoint`, `checkpoint-shadow`, `escalation`, `lead-ticket`, `review`), plus `narrative`, `bench` and `backfill-unknown`.
- **D7 Savings from delegating** (owner, 2026-09-30):
  - **Doing it itself:** lines merged by other agents × the lead's measured dollars per line, from lead tickets of the same difficulty. The seed is M4's L0–L3: 3.5M token-equivalents for 1,979 lines.
  - **Supporting:** the Claude jobs tied to those tickets (ticket writing, directions, escalations, checkpoints, review fixes), plus the tickets' share of planning and review sessions.
  - Net per milestone and per agent, in API-equivalent dollars (Claude Code's `total_cost_usd`; ≈$4 per 1M token-equivalents), with tokens underneath. In `queries.py` (f1-05), shown on the Overview, the milestone page and by `runner report`.
- **D8 Pages** (owner's review of mockup v2):
  - One list per kind, newest first, and a page per item: `/milestones/<key>`, `/tickets/<id>`, `/jobs/<n>`, `/runs/<run_dir>`, `/projects/<name>`. Breadcrumbs run project › milestone › ticket › job.
  - **Milestone page order:** outcome + Done when → what changed + how to test → what next → left for later + how the work went → results, savings, tickets, runs, findings.
  - **Ticket page:** goal, Done when, `depends_on` links, files, result, every job in order, the findings on its code; it links up to its milestone.
  - **Needs you,** at the top of the Overview: open `owner_items` (ADRs a job drafted and the question each asks, blocked tickets, review stops, sign-off waiting with the device steps, setup the owner owes, open owner decisions), a waiting queue with the runner idle, and a runner whose heartbeat stopped mid-job.
  - The edit streak reads "N edits in a row without running a test or check".
  - The sign-off sheet gains **"6. What next"**: the lead's product and factory suggestions (f1-05 amends lead.md and the REVIEW prompt).
  - Later, in `docs/roadmap.md`: an ADRs view, full diffs, before/after screenshots, README rendering.
  - **Amended 2026-10-02 (the owner watching f1):**
    - Needs-you is drawn only when it has items, and refreshes with Running now (one `/live` partial, every 5 s), so "drain the queue" and "heartbeat stopped" go once the runner is back.
    - A rerun resolves the milestone's rerun-kind owner items (`_RERUN_KINDS` in `runner/owner.py`) at session start, and a yes to the reserve resolves its item at once; the closing verdict reopens what still applies.
    - A ticket deleted from `tasks/` leaves the queue: its row stops being `ready`.
    - Plain words only on every page: the agents' own names, "Queue", "Merged", "Checks"; no invented names or abbreviations.

**Replans (the owner asked, 2026-09-30).** Nothing in the ADR 12 flow reviews the plan midway: checkpoints fire only after developer merges, run on Sonnet and read diffs; directions and escalations repair one ticket. f1's risk is in its chains of lead tickets, so two replan tickets sit at the joints where learning happens: after the foundation (07) and after the probes (19). It always writes a dated entry in the Replan log below. The factory review (32) measures them, and recommends whether replans become standard (an ADR, since it changes the flow).

## Risks
- **Lead spend:** 20 lead tickets (2 of them replans) at 0.5–1.5M each is ≈10–20M of Claude, with pauses at usage resets. `runner milestone` restarts itself after each lead ticket that changes `runner/`.
- **Probes need the owner's logins** (above). Without them f1-18 records what's missing, and f1-19 parks the tickets that need it in `tasks/blocked/`, and its dependants wait.
- **The database is outside the repo:** tests never touch the real path, and backfill is idempotent, so running it twice is safe.

## Done when
- All tickets are in `tasks/done/`, and `uv run runner check-all` passes on `main`.
- `uv run runner backfill` run twice gives identical row counts; `uv run runner report m4` reproduces the M4 review's numbers.
- `uv run runner dashboard` serves every page against the real database (screenshots in the review).
- The router and ratings have table tests.
- The review loop ends, and `docs/reviews/f1.md` opens with the sign-off sheet.
