# Notes for developers, in any project

Short on purpose: at most 15 notes (ADR 07). Each holds in any project; a project's own are in its `.softfield/developer.md`.

## Notes
1. If your new test passes before you change any code, the bug may already be fixed on main (f4-23: a finding fixed by two later tickets). Check the code the ticket names, then write `BLOCKED.md`: a first line that is exactly `CATEGORY: false-assumption`, then where main already does it. Don't rewrite the test to make it fail.
2. Test the edges, not only the middle: empty, one, many, the longest note (280 characters), just before and after midnight.
3. Lines stop at 100 characters. Your finish line (`check-all --fix`) formats for you: it joins lines that fit, but won't split a long string (JS inside a Python test). Split only a string that's still too long.
4. Check `.softfield/protected-paths.txt` before your first edit. If the task needs a protected file changed, don't try: write `BLOCKED.md` with `CATEGORY: needs-file` straight away.
5. Before writing an expected list from test data, open the fixture and follow its chain down to its root (`db_path` seeds rows too); never guess what it holds (f6-29 reasoned for an attempt about the threads `write_planning`'s docstring lists). Remember `runner.metrics` upserts: writing a row with an existing key updates it rather than adding one. If the count the test sees differs from yours, trust the page and recount; don't adjust the regex until it matches (f6-09 wrote "4 things" for three replies without finding the fourth, the fixture's ripe milestone).
6. If `all-tests` fails in a test about another ticket or a file outside your `files:` (f1-35: `test_tasks.py` naming f1-36), or `layout` names a file you never made (f13-01: a review's scratch file), main was red before you. Don't try to fix it: finish your own work and write `BLOCKED.md`: a first line that is exactly `CATEGORY: needs-file`, the failing test's or file's name on the next line.
7. When a number in your ticket disagrees with your count, write the rows out as a table (duration in seconds, each token column) and add them once; never change fixture rows or invent new ones to make a number fit. When your test and your code disagree, the ticket's Context decides which is wrong: never change an assertion that quotes the ticket to match your code (f8-06 posted `seven_day` where the ticket said `week`, then rewrote its test to agree).
8. A ticket that replaces a behaviour replaces its tests: rewrite the tests in your `tests:` that pin the old one, and never leave an assertion that can't fail. Keep them as narrow: an assertion within a panel that goes moves to the panel that replaces it, never to the whole page (f3-05). Assert your setup first: a test that one status outranks another checks the rival really shows it (f132-01's read "Idle", not "picking the next ticket", and passed under either order). When a list an existing test asserts grows, assert the whole new list, never its first rows (`[:5]`): the reviews of F173 and F154 both found an edit cut that way.
9. `check-all` takes about 5 minutes. Run it with no `timeout` (the default is 15 minutes) and never a shorter one: f109-03 gave it 300000 twice, lost 10 minutes and learned nothing. "(no output)" after a shell timeout means the call was killed, not that the checks hang; never write `BLOCKED.md` for it.
10. To add to an existing file, Edit it, anchored on its last lines; never Write it: Write replaces the whole file (f2-07 wiped the 1,300-line dashboard `conftest.py` and lost the attempt). You can't delete or rename files, so create only those your ticket names: f3-16 made two empty ones and spent its last attempt failing to remove them.
